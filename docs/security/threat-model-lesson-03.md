# Threat model: lesson 3 (likes, domain events, GraphQL)

> Extends the [lesson 2 threat model](threat-model-lesson-02.md) and the [lesson 1 one](threat-model-lesson-01.md). Only the new and changed items are listed; T1–T36 still apply.

Trust boundaries added or changed: gateway ↔ `likes`; `videos` and `comments` → `likes` (events over internal HTTP); `comments` and `likes` → the future `lake` subscriber (no receiver yet, rows wait in the outbox); browser → **GraphQL layer inside the gateway** → services (the caller's token is forwarded). Architecture — [ADR 0011](../adr/0011-likes-service-and-domain-events.md), [ADR 0012](../adr/0012-graphql-at-the-gateway.md), domain [Engagement](../domains/engagement.md).

| # | STRIDE | Threat | Mitigation | Verification |
| --- | --- | --- | --- | --- |
| T37 | Elevation / Spoofing | IDOR on likes: liking or unliking on behalf of another user; liking content the caller cannot see | The liker is always taken from `sub`, never from the path or body; a target must be known to the service (a video not deleted, a comment that belongs to the video in the path), otherwise 404 — an unknown, deleted and not-yet-processed target are indistinguishable | `AC_likes_02`, `AC_likes_04` |
| T38 | Tampering / DoS | Like abuse: ballot stuffing, flooding of like/unlike toggles, counter manipulation | One like per (target, user) by primary key; likes are idempotent (no second row, no second event); the counter changes in the same transaction as the like row (no drift); batch counters limited to 50 ids. Residual risk: many accounts can still inflate counts; REST like routes are not rate-limited (only upload creation and GraphQL are) | `AC_likes_03`, `AC_likes_07`, `AC_events_05` |
| T39 | Spoofing / Elevation | Forged calls to the internal intake routes of `likes` (`/internal/v1/events/video-processed`, `video-deleted`, `comment-added`, `comment-deleted`) — creating fake likeable targets or deleting real ones | `X-Internal-Key` (constant-time comparison, empty key = closed), not routed by the gateway (404), the service publishes no port; ids and `schemaVersion` validated (400). Residual risk: one `INTERNAL_API_KEY` for all services (T33) | `AC_likes_09`, `AC_likes_12`, `AC_gateway_03` |
| T40 | Tampering | Duplicate, reordered or late events resurrect deleted data (a late `video.processed.v1` after `video.deleted.v1`, a late `comment.added.v1` after `comment.deleted.v1`) | Idempotent intake by ids; deleted videos and comments stay as tombstones in `known_videos` / `known_comments`; deletion cascades likes and counters | `AC_likes_10`, `AC_likes_11` |
| T41 | Info disclosure | Private content leaves the system through domain events (comment text, free text) | The comment text is **never** published: `comment.added.v1` carries `textLength` only; events carry opaque ids (`userId`, `videoId`, `ownerId`, `commentId`), no names, e-mails or phones. The lake receives nothing yet (rows wait locally); no per-comment events for cascades | `AC_events_01`, `AC_events_07`, `make demo` (no comment text in any payload) |
| T42 | Info disclosure | The liker list reveals who reacted | Deliberate: likers, counts and `likedByMe` are visible to any authenticated user, like profiles and follower lists; anonymous access does not exist. Paging is bounded (limit ≤ 50, keyset cursor, a malformed cursor is ignored) | `AC_likes_08` |
| T43 | DoS | GraphQL query abuse: deep nesting, huge pages, aliases or repeated fields that fan out to many downstream calls, oversized documents | Maximum execution depth 8 (deeper queries are rejected before execution), page size ≤ 50 (feed ≤ 30; larger values are rejected without calling services), request body ≤ 64 KiB, execution timeout 20 s, per-user rate limit (300 requests per minute), DataLoaders keep fan-out to one downstream call per service per level. Residual risk: there is no query complexity (cost) analysis; repeated aliases up to the body limit are bounded only by the limits above | `AC_graphql_02`, `AC_graphql_09`, `AC_graphql_10` |
| T44 | Info disclosure | Schema discovery through introspection | Introspection is off by default (`GraphQL:AllowIntrospection=false`) and switched on only for the local stack; no IDE page is mapped; the schema is documented in `contracts/graphql/gateway.graphql` anyway, so it is not a secret — the point is to avoid exposing it in non-local environments | `AC_graphql_11`, `AC_graphql_13` |
| T45 | Spoofing / Elevation | Token forwarding: the gateway calls services on behalf of the user (confused deputy, token leak, SSRF) | `/graphql` requires the same JWT as REST (`authenticated` policy, 401 otherwise); only the **caller's own** `Authorization` header is forwarded, never a gateway-minted or elevated token; service addresses come from configuration, not from the query, so a client cannot redirect the header; services validate the token again (zero trust: signature, issuer, audience); `/internal/**` and the internal key are never used by GraphQL; the header is not logged | `AC_graphql_01`, `AC_graphql_12` |
| T46 | Info disclosure | Error messages leak internals of downstream services | Failures map to stable codes (`NOT_FOUND`, `VALIDATION`, `UNAVAILABLE`, `FORBIDDEN`) with generic messages; the original exception is dropped | `AC_graphql_07`, `AC_graphql_08` |
| T47 | Elevation | GraphQL mutations bypass the rules of REST | Mutations call the same REST endpoints with the caller's token, so ownership checks (comment delete by author or video owner, follow rules, like idempotency) are enforced by the services, not by the schema | `AC_graphql_04`, `AC_graphql_05`, `AC_graphql_06` |

## Changed items of earlier lessons
- **T15 (direct access bypassing the gateway):** the `likes` port is not published; the service validates the JWT itself.
- **T18 (shared DB leak):** a new database and role `likes` (`LIKES_DB_PASSWORD`); the outbox tables live in the producer's own DB.
- **T25 (cascade of deletion):** `likes` joins `analysis` and `comments` as a subscriber of `video.deleted.v1`; tombstones also protect likes (T40).
- **T33 (shared internal key):** now used by `likes` intake and by the outbox dispatchers of `comments` and `likes` as well.

## Residual risks
- No complexity analysis for GraphQL; rate limits cover upload creation and `/graphql` only — REST likes, comments and follows are not rate-limited.
- Likes can be inflated with many accounts (no anti-abuse beyond one like per user and target).
- The `lake` outbox rows contain behaviour data (who liked what) and wait unprotected in the service databases until lesson 4; access is limited by DB-per-service roles.
- A single internal key is shared by all services (T33).
